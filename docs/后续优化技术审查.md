# 后续优化：技术审查与探索实验

日期：2026 年 11 月 12 日  
审查基线：`0c7e9f4` / V1.2.0  
性质：现状分析及待实施建议，不是新增功能验收报告。

本轮没有修改业务源码或重新发布 APK。审查结合静态代码、调用现有编译产物的 JVM 实验，以及独立模拟器内的界面检查。未访问用户真实健康记录。

## 1 发现与证据等级

A：已有可重复实验或界面证据；B：代码路径明确，但未完成相应设备复现；C：优化假设，必须先测量。结构确认不等于性能影响已经量化。

| 编号 | 现状 | 证据与范围 | 建议 |
| --- | --- | --- | --- |
| A01 | 普通实际录入弹窗关闭时没有未保存提示 | B；`Forms.kt` 的 `ExecutionForm` 调用 `FormDialog` 未传 `dirty`，默认为 false；专注模式有自己的退出保护 | 为普通实际录入独立比较初始值，覆盖数字、状态和原因；不要直接关闭并丢弃输入 |
| A02 | 日期回拨会使已有历史在全量校验中被拒绝 | A；同一份合法样本在 2026-11-12 校验通过，改为 11-11 后因存量日期抛出异常 | 分离新增/改日期校验与历史结构校验，历史日期保持原归属 |
| A03 | 草稿日期在不同位置的统计口径不一致 | A；只保留一条 DRAFT 实际记录时，趋势日期筛选得到 1，`weekOverview` 训练天数为 0 | 先统一“有已完成动作”口径；未来若统计已确认组，所有入口一起改变定义 |
| A04 | 图表处理任意方向拖动并消费事件 | B；`WeightChart` 使用 `detectDragGestures` 并调用 `consume()`，没有方向判断 | 横向查询与纵向页面滚动分别处理；用固定小样本复现并回归 |
| A05 | 跨年全历史横轴只显示月/日 | A/B；`WeightChart` 日期格式为 `M/d`；五年样本可显示，但年份语义不充分 | 跨年时显示年份、选点显示完整日期；不要改变原始日期或均值算法 |
| A06 | 训练日期条是普通横向 Row，全部日期逐项组合 | 结构确认；`TrendsScreen` 对去重后的日期 `forEach`；五年样本有 782 个训练日 | 优先改为惰性容器或按月入口；保留完整可访问历史 |
| A07 | 每次修改前读取完整快照、全量校验；观察流也返回全量快照 | 结构确认；`FitnessRepository.mutate/data` 与 `FitnessDao.snapshot` | 先分段测量 DB 读取、解码、校验、写入和 UI 更新，不能直接把耗时归因于某一层 |
| A08 | 最近动作最多 20 条，同名＋类型作为去重及历史匹配依据 | B；`recentExercises`、`ExercisePicker`、`previousExecution` | 最近列表继续小而快；完整搜索与历史归集另用稳定动作身份 |
| A09 | 专注训练没有当次加减组，也没有有氧运动计时 | B；`ValuesFields` 在逐组模式隐藏增删组；时长/距离仅输入文本 | 稳定组 ID 后做增删；新增有氧计时状态，不能复用休息计时字段 |
| A10 | 恢复点按墙上时钟限流，回拨后可能长时间不再生成 | A；将最近恢复点修改时间置为当前时间＋一天，下一次 `save` 仍只有 1 个文件；对照目录将时间设为当前时间－两分钟，再保存得到 2 个 | 进程内用单调时钟限流；跨进程识别未来修改时间，防止负差值一直抑制生成 |
| A11 | 小屏/大字体中核心动作需要额外滚动 | A；API 28、200% 字体，以及约 320 dp 宽＋130% 字体截图 | 称重后收起大卡、缩短重复说明，使用自适应行列；不强行缩小系统字体 |
| A12 | 提醒开启状态未单独反馈通知渠道是否被关闭 | B；`allowed` 检查总通知和运行时权限，未检查渠道重要程度 | 页面分别显示应用偏好、总权限和渠道状态，允许进入系统处理 |

“未保存提示”需要针对普通实际弹窗补齐，不应把已有称重和专注模式的保护误写为全部缺失。以上均为后续工作项，并未在本轮偷偷修改已交付版本。

## 2 日期边界：怎样避免改一条记录却被旧数据挡住

当前 `Rules.validate` 遍历所有体重和实际记录，针对传入的 today 调用 `pastDate`；`mutate` 每次保存都会调用它。该行为确保了正常设备日期下不能新增未来实际，但也把保存时的设备日期作为所有存量记录的有效性条件。

因此，当系统日期回拨或跨时区使本地日期退回前一天时，一条之前合法的记录可能阻断其他无关修改。本轮通过生产编译类复现了校验拒绝；没有修改系统时间来对用户数据做实验，也没有把它描述为所有时区切换都会出现。

建议分为三层：

1. 新增体重、实际和改归属日期：用统一 Clock 校验操作日期；所有写入入口都必须执行，不能仅依赖 UI。
2. 已有数据结构：验证唯一 ID、正数、字段类型、关联及状态；不因本地日历短暂退回而自动失效。
3. 外部导入：结构严格校验；超出当前日历日的记录明确展示并按制定的恢复规则处理，不能静默改日、删行或默认信任外部时间戳。

本地日期和时区从统一可测试的时钟提供。打开的训练保持原归属日；首页在重新进入前台、日期/时区变化时刷新，当前录入不被自动移动。恢复点限流与提醒排期同时检查回拨边界。

## 3 长历史样本

固定结束日期为 2026-11-12；每天一条体重，每周一/三/五六个模拟项目：三个力量、两个时长、一个距离项目。每项实际均完成，力量各三组；无模板。频次仅用于生成数据，不是对用户的训练建议。

| 样本 | 体重 | 计划日 | 实际项目 | 紧凑 JSON 字节数 |
| --- | ---: | ---: | ---: | ---: |
| 1 年 | 365 | 156 | 936 | 646,201 |
| 5 年 | 1,826 | 782 | 4,692 | 3,237,689 |
| 10 年 | 3,652 | 1,565 | 9,390 | 6,478,885 |

所有样本均由当前 `BackupCodec.decode` 和 `Rules.validate` 接受，不是绕过校验直接往数据库塞非法记录。包含中文、目标快照、实际值、确认组和单位。

### 3.1 桌面 JVM 结果

环境：Windows、JDK 17.0.10，使用当前 Debug 的 Kotlin 编译产物及相同 Kotlin/序列化依赖；最大 Java 堆 1 GB。校验、趋势和月历分支预热 8 次、采样 31 次；JSON 预热 3 次、采样 11 次。表中为单进程探索实验的中位毫秒值。

| 样本 | 全量校验 | 完整 JSON 解码校验 | JSON 编码 | 全历史趋势点 | 30 日状态查询 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 年 | 5.962 | 40.214 | 2.666 | 1.355 | 0.913 |
| 5 年 | 13.469 | 128.593 | 11.019 | 1.487 | 1.019 |
| 10 年 | 26.364 | 209.991 | 22.377 | 2.086 | 2.247 |

这些不是手机操作延迟。实验未覆盖 Room、磁盘、Compose、文件提供者和恢复点写入，不使用它证明冷启动或帧率达标。预热、JIT、运行顺序、GC 和宿主负载会影响结果；并非 JMH 或标准性能回归套件。原始数据含样本百分位，但不将 11 次采样的百分位当作正式 SLA。

结论：统计计算并未呈现需要立即替换算法的证据；完整数据校验和序列化的成本随历史量增加。优先查清保存链路与 UI 列表的成本，不先更换技术栈。

### 3.2 Android 探索

使用独立 API 28 模拟器和 `.debug` 包，通过系统文件选择器导入五年 JSON；经过替换范围预览，先保存原数据安全副本，再恢复。界面确认显示 1,826 条体重、782 日计划、4,692 条实际；全历史范围可以展示 1,826 个测量点。正式包没有被这批长历史样本覆盖。

切换全历史及检查界面时，日志出现多条 Choreographer 跳帧提示。后续减少 UI Automator 调用的尝试仍观察到一次 `Skipped 469 frames`。这提示需要专项定位；它不能直接换算为用户手机上的平均延迟，也不能证明单一代码行就是原因。

本轮 `dumpsys gfxinfo` 获取失败并伴随 Broken pipe，因此没有可用的帧耗时分布。没有据此声称 ANR、崩溃、内存泄漏或某个优化已经解决卡顿。截图可用于确认内容，不是流畅性的证据。

采用 Debug 包、模拟器和检查工具会改变性能。下一步应在 Release/profileable 构建、可控设备和固定动作下，用 Macrobenchmark/Perfetto 区分数据库、主线程计算、列表组合与绘制。[Android Macrobenchmark](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview)

## 4 大字体与窄屏

已实际检查：正常物理尺寸 1080×1920、420 dpi 下 200% 字体的首页、计划、专注训练和月历；另以 840×1493 的显示覆盖模拟约 320 dp 宽，字体 130%，检查首页和专注训练。两种配置均为 API 28 模拟器，不代表所有设备的非线性字体缩放。

观察：系统字体增大后主要内容可读，计划周视图仍保留七天，但头部说明、体重卡和训练组输入占据更多纵向空间。需要滚动访问后续操作；据此建议改信息层级和布局，而不是宣称所有页面不可用。

自动点击脚本有两次未找到按钮：一次按钮在首屏外，另一次首页保留了较低的滚动位置、脚本只向下查找。调整查找后取得了主要截图；窄屏称重表单未完成本轮验收。脚本失败不能被包装为 App 功能失败。

检查结束后已将模拟器字号恢复 1.0，显示大小恢复 1080×1920。未安装或启用 TalkBack，未验证 200% 字体＋软键盘＋窄屏的所有组合。

Android 官方建议结合自动检查与 TalkBack 等实际操作；本轮大字体截图不等于完成了可访问性验收。[Compose 可访问性测试](https://developer.android.com/develop/ui/compose/accessibility/testing)

## 5 数据模型的下一步

### 5.1 先区分四种身份

| 身份 | 用途 | 不应使用的替代物 |
| --- | --- | --- |
| 动作定义 ID | 关联同一个动作跨日期的历史和固定提示 | 用户可修改的名称 |
| 日期内项目 ID | 关联计划项目及其实际记录，继续保留现有 ID | 名称＋日期拼接 |
| 实际训练组 ID | 增删或排序后保持组记录及确认状态 | 列表下标 |
| 模板/生成批次来源 ID | 模板差异、重复排期幂等与未来副本预览 | 计划名称 |

旧记录不按名称自动合并为同一个动作。对可能相同的动作展示候选，用户明确归并后记录映射；哑铃、器械、辅助重量和单只/总重量语义不明时保持分开。

旧下标确认组迁移到稳定组 ID 时，应对同一存量记录产生可重复的标识，例如依据实际记录 ID 和原始位置生成。**不能在每次反序列化的默认字段里随机生成 ID**，否则读取同一份历史也会改变身份。

### 5.2 整场状态与逐项完成状态分开

结束整场只表示用户暂时或明确收尾，不把每个项目变为 DONE。现有每日“全部完成/含跳过已结束/进行中”仍由项目推导；新增会话状态表示未开始、进行、暂停与已结束，两者分别展示。

整场总历时只在明确开始/暂停/结束后计算，训练组不反推持续时间。有氧运动用时与整场总历时分开；同一场里做力量后跑步，不把前半场时间算进配速。

进程重建使用持久化确认记录恢复；未提交数字与数据库实际值分开，按草稿策略恢复。取消退出提示不能覆盖已保存组。

### 5.3 迁移与备份

新增字段先评估能否兼容现有 JSON payload；需要查询/约束的字段再考虑提取为 Room 列。当前表结构是 schema 1，不能为了版本命名直接增加数据库版本。

确需改表时提供显式 Migration 与旧数据库样本测试，不允许破坏性重建。需要备份 v4 时继续接受 v1/v2/v3，明确旧版不能读取 v4；迁移后的克数、历史快照、确认组和关联 ID 逐项比对。

外部完整恢复仍用一个事务。自动备份和本机恢复点不能与主保存共享“失败就全部取消”的语义：先确保用户记录写入，再单独反馈保护副本状态；破坏性恢复前的外部安全副本仍必须成功。

## 6 性能改造顺序

1. 在小样本和五年样本上分别记录保存各阶段耗时；UI 使用 profileable/Release，测量工具和设备状态写进报告。
2. 先处理无上限的日期 Row、滚动手势和全历史轴；使用 LazyRow 或按月入口，图表大范围可采用仅用于绘制的抽稀，选点和统计仍读原值。
3. 如全量观察流确为瓶颈，增加日期范围/单项目查询与索引映射。现有 plan/item 关联可用于按日期查询，部分改进不必改表。
4. 如逐组保存仍超预算，把局部写入与完整恢复校验分开。写入保留外键、关联、状态和单位检查，不以提升速度为由省略约束。
5. 只有实际测量证明必要时，再扩展表结构、缓存和统计预计算；用回归基准防止下一次新增功能变慢。

不要把 `Statistics.points` 简单替换为“最近七条记录平均”，不要为了画得连续补零，也不要对数据源做永久抽稀。

## 7 最小技术债处理

- 页面间输入保护统一约定：外部关闭、系统返回、明确取消和保存成功分别处理；有效输入清空为非法输入时仍算已修改。
- 所有实际录入入口共用相同的确认规则；部分字段更新不意外重置已确认组，主动改组则明确重新确认。
- 权限状态不等于功能偏好。通知总开关、单渠道和 Android 13+ 授权分别可解释。
- 可恢复错误使用简短用户提示，日志避免完整健康备份、输入内容和长序列化片段。
- 新功能不先增设网络、位置或广泛文件权限；按实际能力最小化申请。
- 当前少量 Lint 图标/写法建议可随界面改动处理，不把它们排在数据边界问题之前。
